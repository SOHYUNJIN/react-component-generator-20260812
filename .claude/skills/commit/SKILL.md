# commit: 논리 단위별 컨벤션 커밋

변경사항을 분석해 목적이 다른 변경끼리 섞이지 않도록 나누고, 단위마다 한국어 conventional commit 메시지로 커밋한다. 여러 목적이 뒤섞인 채로 커밋되면 나중에 `git log`나 `git blame`으로 "이 줄이 왜 바뀌었는지" 추적하기 어려워지므로, 쪼개는 작업 자체가 이 스킬의 핵심 가치다.

## 전제 확인

- 현재 디렉토리가 git 저장소가 아니면 그 사실을 알리고 중단한다 (`git init`을 대신 실행하지 않는다).
- 위험하거나 되돌리기 어려운 git 작업(`--amend`, `--force`, `reset --hard`, `--no-verify`, `--no-gpg-sign`)은 사용자가 이 요청에서 명시적으로 지시하지 않는 한 하지 않는다.
- 사용자가 먼저 요청하지 않는 한 push하지 않는다. 커밋까지가 이 스킬의 기본 범위다.

## Step 1: 변경사항 파악

- `git status`로 전체 상태를 확인한다 (대형 저장소에서 메모리 문제를 일으킬 수 있는 `-uall` 플래그는 쓰지 않는다).
- `git diff` (unstaged)와 `git diff --staged` (이미 staged된 것)를 모두 확인한다 — 둘 다 커밋 대상이 될 수 있다.
- `git log --oneline -10`으로 이 저장소가 이미 쓰고 있는 커밋 메시지 컨벤션을 확인한다. 이미 다른 형식(예: 티켓 번호 prefix)을 일관되게 쓰고 있다면, feat/fix/refactor/chore 형식으로 강제 전환하기 전에 사용자에게 알리고 원하는 방식을 확인한다.
- 변경사항이 전혀 없으면 "커밋할 변경사항이 없습니다"라고 안내하고 종료한다.

## Step 2: 논리적 단위로 분류

판단 기준은 "같은 목적을 위한 변경인가"이다. 파일이 여러 개라도 하나의 기능이나 하나의 버그 수정을 위해 함께 바뀌었다면 한 단위로 묶는다. 반대로 한 파일 안에서도 서로 무관한 목적의 변경(hunk)이 섞여 있다면 분리 대상이다.

실무적인 분류 예:

- 새 기능 코드 + 그 기능을 쓰기 위해 필요했던 연관 수정 → 한 단위 (`feat`)
- 기존 로직의 잘못된 동작 수정 → 별도 단위 (`fix`)
- 동작 변화 없이 구조만 개선(이름 변경, 함수 추출, 중복 제거 등) → 별도 단위 (`refactor`)
- 빌드 설정, 의존성 버전, 포맷팅, 주석/문서, 스크립트 등 그 외 잡무 → 별도 단위 (`chore`)

한 파일 안에 서로 다른 단위에 속하는 hunk가 섞여 있으면 `git add -p`로 hunk 단위 스테이징을 고려한다. 분류 결과 단위가 하나뿐이면 억지로 쪼개지 않는다 — 쪼개기는 목적이지 규칙이 아니다.

## Step 3: 단위별 커밋 메시지 작성

형식: `<type>: <한국어 요약>`

- `type`은 반드시 `feat` / `fix` / `refactor` / `chore` 중 하나다. 이 넷에 명확히 들어맞지 않는 변경(문서, 테스트, 스타일 등)은 가장 가까운 것으로 판단하되 보통 `chore`로 분류한다.
- 요약은 한국어로, 무엇이 바뀌었는지 한 줄로 간결하게 쓴다 (72자 내외).
- 왜 바뀌었는지가 diff만으로는 드러나지 않고 중요한 맥락이라면, 빈 줄을 두고 본문에 이유를 덧붙인다. 자명한 내용을 굳이 본문에 반복하지 않는다.

type 판단 기준:

- `feat`: 사용자가 체감할 수 있는 새 기능이나 동작 추가
- `fix`: 버그, 잘못된 동작, 예외 상황 수정
- `refactor`: 겉보기 동작은 그대로 두고 코드 구조를 개선
- `chore`: 빌드/설정/의존성/포맷팅 등 위 셋에 속하지 않는 잡무성 변경

## Step 4: 커밋 계획 제시 및 승인

실제로 커밋을 실행하기 전에, 다음과 같은 표로 계획을 보여주고 사용자 승인을 받는다.

```
| # | 타입 | 커밋 메시지 | 포함 파일 |
|---|------|-------------|-----------|
| 1 | feat | 로그인 폼에 이메일 형식 검증 추가 | src/LoginForm.tsx |
| 2 | fix  | 날짜 파싱 시 하루 밀리는 오류 수정 | src/utils/date.ts |
```

사용자에게 다음 선택지를 제시한다: **전체 승인** / **일부만 승인** / **메시지 수정 요청** / **취소**. 승인받지 않은 단위는 커밋하지 않는다.

## Step 5: 승인된 단위만 순서대로 커밋

- 파일 단위로 `git add <구체적인 파일 경로>`를 사용한다. `git add -A`나 `git add .`처럼 전체를 한 번에 스테이징하지 않는다 — 다른 단위의 변경이나 의도치 않은 파일이 섞여 들어갈 수 있다.
- 스테이징하기 전 `.env`, `credentials.json`, `*.pem` 등 시크릿으로 의심되는 파일이 대상에 포함돼 있는지 확인한다. 포함돼 있으면 그 커밋 단위에서 제외하고 사용자에게 알린다.
- 커밋 메시지는 항상 heredoc으로 전달해 개행이나 특수문자가 깨지지 않게 한다.
- 각 커밋 뒤 `git status`로 의도한 파일만 반영됐는지 확인한다.
- 여러 단위를 순서대로 커밋한 뒤, 최종 `git log --oneline -n <개수>`로 결과를 사용자에게 보여준다.

## 하지 말아야 할 것

- 서로 다른 목적의 변경을 하나의 커밋으로 뭉치기
- 영어 커밋 메시지나 `feat`/`fix`/`refactor`/`chore` 외의 임의 prefix 사용
- 사용자 승인 없이 커밋 실행
- `git add -A` / `git add .`로 전체 스테이징
- 시크릿으로 의심되는 파일을 확인 없이 커밋에 포함
- 사용자가 요청하지 않은 `--amend`, `--force`, `--no-verify` 사용이나 push
