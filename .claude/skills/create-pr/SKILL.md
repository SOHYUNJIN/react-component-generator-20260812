# create-pr: 이중 언어 PR 생성

현재 브랜치의 커밋을 분석해 PR 제목과 한국어+영문이 모두 담긴 본문을 작성하고, 사용자 승인을 받은 뒤 실제 원격 작업(push, `gh pr create`)만 서브에이전트에 위임해 실행한다. 본문 작성과 실제 생성 단계를 분리하는 이유는 명확하다 — 제목·본문은 되돌리기 쉬운 초안이지만, push와 PR 생성은 다른 사람에게 보이는 되돌리기 어려운 작업이므로 사용자가 내용을 직접 확인한 뒤에만 실행되어야 한다.

## Step 0: 저장소 지침 로드

저장소 루트의 `AGENTS.md`(없으면 `CLAUDE.md`)를 읽어 커밋 컨벤션, 빌드/테스트 명령을 파악한다. 이 저장소는 커밋에 `commit` 스킬을 쓰도록 되어 있다 — PR을 만들기 전에 커밋이 이미 그 컨벤션을 따르고 있는지 참고한다.

## Step 1: 현재 상태 파악

다음을 병렬로 확인한다:

- `git status` (대형 저장소에서 문제를 일으킬 수 있는 `-uall` 플래그는 쓰지 않는다) — 커밋되지 않은 변경사항이 있는지 확인한다.
- 현재 브랜치가 원격을 추적하고 있는지, 원격보다 앞서 있는지(push 필요 여부).
- 기본 브랜치 확인: `gh repo view --json defaultBranchRef -q .defaultBranchRef.name` 또는 `git symbolic-ref refs/remotes/origin/HEAD`로 조회한다. 실패하면 `main`을 기본값으로 가정하되 사용자에게 확인한다.
- 현재 브랜치가 기본 브랜치 자체라면 PR을 만들 대상이 없다는 뜻이므로, 사용자에게 알리고 중단한다 (임의로 새 브랜치를 만들지 않는다).

**커밋되지 않은 변경사항이 있으면 먼저 처리 여부를 사용자에게 확인한다.** 이 스킬이 대신 커밋하지 않는다 — `commit` 스킬로 넘기거나, 사용자가 직접 정리하도록 안내한다.

## Step 2: 변경 내역 분석

- `git log <base>..HEAD --oneline`으로 이 PR에 포함될 커밋 목록을 확인한다.
- `git diff <base>...HEAD`로 실제 변경 내용을 확인한다. 커밋 메시지만으로는 "왜"가 드러나지 않는 경우가 많으므로 diff를 직접 읽고 의도를 파악한다.
- 커밋이 하나면 그 커밋 메시지가 이미 좋은 요약일 가능성이 높다. 커밋이 여러 개면 논리 단위(기능/버그수정/리팩터/잡무)로 묶어서 요약한다.

## Step 3: PR 제목·본문 초안 작성

- **제목**: 전체 변경을 한 줄로, 70자 내외. 가장 중요한 변경을 기준으로 쓰고, 커밋 메시지 스타일을 참고하되 그대로 이어붙이지 않는다.
- **본문**: 항상 한국어 섹션과 영문 섹션을 모두 포함한다. `references/pr-template-ko.md`와 `references/pr-template-en.md`를 각각 읽고, 그 구조를 따라 Step 2에서 분석한 내용으로 채운다. 두 템플릿을 아래 순서로 하나의 본문에 합친다:

  ```
  <한국어 섹션 채운 내용>

  ---

  <English section, filled in>
  ```

  두 섹션의 내용은 번역 관계여야 한다 — 같은 PR에 대해 서로 다른 근거를 말하지 않는다. 템플릿에서 채우지 못한 섹션(예: 관련 이슈 없음)은 통째로 삭제한다.

## Step 4: 사용자 승인

push나 PR 생성을 실행하기 전에, 작성한 제목과 본문 전체를 그대로 보여주고 다음을 확인한다:

- **승인**: 그대로 진행
- **수정 요청**: 지적한 부분만 고쳐서 다시 제시
- **취소**: 아무 원격 작업도 하지 않고 종료

승인 없이는 Step 5로 넘어가지 않는다.

## Step 5: 서브에이전트에 PR 생성 위임 (`subagent_type: fork`)

승인을 받은 뒤에만, 실제 원격 작업을 `Agent` 도구로 서브에이전트에 위임한다. `subagent_type: "fork"`를 사용한다 — fork는 지금까지의 대화 컨텍스트(분석한 diff, 확정된 제목·본문)를 그대로 이어받으므로 별도로 배경 설명을 반복할 필요가 없고, 동시에 실제 push/PR 생성이라는 부수효과를 별도 실행 단위로 분리해 무엇이 실행됐는지 명확히 남길 수 있다.

- 결과 URL이 바로 필요하므로 `run_in_background: false`로 포그라운드 실행한다.
- 서브에이전트에게는 **Step 4에서 이미 승인된 제목·본문을 그대로** 전달한다. 서브에이전트가 내용을 다시 요약하거나 새로 작성하게 하지 않는다 — 서브에이전트의 역할은 승인된 내용을 정확히 실행하는 것이지, 콘텐츠를 재창작하는 것이 아니다.
- 프롬프트에 포함할 것:
  - 필요 시 `git push -u origin <현재 브랜치>` 실행 (이미 최신이면 생략)
  - `gh pr create --title "<승인된 제목>" --body "$(cat <<'EOF' ... EOF)"` — 본문은 반드시 heredoc으로 전달해 개행·특수문자가 깨지지 않게 한다
  - 생성된 PR URL을 결과로 반환할 것
  - `--base`, `--draft` 등 사용자가 명시적으로 요청한 옵션이 있으면 포함할 것

서브에이전트가 반환한 PR URL을 사용자에게 그대로 전달한다.

## 하지 말아야 할 것

- 사용자 승인 없이 push나 `gh pr create` 실행
- 커밋되지 않은 변경사항을 이 스킬이 대신 커밋하기 (그건 `commit` 스킬의 역할)
- 기본 브랜치에서 곧바로 PR 생성 시도
- 한국어/영문 중 한쪽만 작성하고 다른 쪽을 생략
- 서브에이전트에게 제목·본문을 다시 작성하게 하거나 요약만 던져주고 알아서 채우게 하기
- `--force` push, `--no-verify`, 커밋 amend 등 사용자가 명시적으로 요청하지 않은 파괴적 작업
- PR 리뷰 코멘트 반영 작업 (그건 `autofix` 스킬의 영역)
